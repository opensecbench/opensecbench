# OpenSecBench design docs — ADRs

Architecture Decision Records (ADRs) and open-format specifications. Per our working agreement,
**a short design doc lands here before its subsystem is built**, and docs are kept current as
decisions change.

New here? Start with [ADR-0001](adr-0001-architecture-overview.md) for the architecture and its
boundaries. Contributing a change that makes or alters a design decision? Read
[ADR-0057](adr-0057-decision-process.md) for when an ADR is required and how the process works, then
copy [`adr-template.md`](adr-template.md) to start one.

## Conventions

- One ADR per decision; format: **Context → Decision → Consequences**. Copy [`adr-template.md`](adr-template.md) to start.
- Number ADRs sequentially; never renumber or delete. Supersede rather than silently rewrite, and note status changes (`Proposed` → `Accepted` → `Superseded by ADR-XXXX`).
- **Propose before building big.** For a change that makes or alters a decision, open a `Proposed` ADR (or an issue) *before* the large PR, so the design is reviewed before the code. See [ADR-0057](adr-0057-decision-process.md).
- The index table above is generated — run `make adr-index` after adding or restatusing an ADR; CI fails if it's stale.
- Format specs (capability manifest, extension package, playbook, project template) are versioned JSON Schemas under `spec/` once they stabilize; ADR-0003 defines their shape.

Later subsystems get an ADR when their phase begins. See [`../../TODO.md`](../../TODO.md).
